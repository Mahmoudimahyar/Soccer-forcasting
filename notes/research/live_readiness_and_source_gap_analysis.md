# Live-readiness and source-gap analysis — in-play feature families

`research_only / experimental / not_runtime_approved / not_trade_eligible / not_live_eligible`

Generated by `scripts/build_live_readiness_matrix.py` from local validated artifacts only.
Outputs: `data/reference/live_readiness_matrix.{csv,json}`. **No 2026 WC data used. No provider
purchase recommendations. No market claims.**

## The one fact that drives everything

Every local artifact is **post-hoc and complete-match**. The only time coordinate is the
**match-clock minute** (`elapsed`), which is what makes leakage-safe *offline replay* possible.
**No source carries a wall-clock event *publication* timestamp.** Therefore a family can be fully
point-in-time *replayable offline* and still be **not live-eligible**, because we have never
measured how long after an on-field event a live provider would actually publish it. We keep two
columns distinct:

- `point_in_time_replay_possible` — offline, match-clock gated → **yes for almost every family**.
- `classification` / `live_eligible` — needs measured provider latency + rights + schema parity.

This is why **zero** families are classified `live_eligible`: not because they are unusable, but
because the live-latency evidence has never been collected.

## Reading the three blocked classes

**`blocked_by_latency` (3).** Discrete or near-discrete signals (team shot counts, possession
share, corners/free-kicks) that API-Football *does* deliver, but whose **live publication latency
and revision rate are unmeasured**. These are the cheapest to unblock: instrument a live feed,
measure latency on ≥20 matches, causal-gate.

**`blocked_by_missing_provider_contract` (5).** xG-family + StatsBomb-specific event types (pressure).
StatsBomb open data is **post-hoc and non-commercial**; API-Football has xG only for newer
tournaments and **no shot-location xy** at all. A *live* version needs a live xG / spatial provider
contract that does not exist on disk. Research already showed in-play xG **did not beat** score+Elo,
so these are low-ROI to unblock.

**`blocked_by_no_point_in_time_history` (6).** Spatial possession-chain families (field tilt, box
entries, deep progression, transitions) need a granular live event-location stream API-Football
lacks; plus **weather** (no as-of-timestamped weather history is in the validated local set) and
**in-play odds** (only *pre-match* odds snapshots exist locally — there is **zero** in-play-odds
history to backtest a live market feature against).

## The six `potentially_live_with_verified_provider` families

These are the realistic near-term live candidates because API-Football's Pro coverage for them was
**empirically verified** (lineups/player-ids/positions, goals/cards/subs with minute+player). They
are gated only by **measuring live publication latency** and confirming clock/regulation semantics
live. Caveat from prior research: the **player/lineup plane is an honest negative** vs Elo on
pre-match 1X2, so among these, the load-bearing ones are **score / time / players / cards / subs**
— exactly the W2-reference inputs.

## What would have to be true before any live claim (per family: see CSV)

For every family the CSV lists `required_provider_fields`, `required_cadence`,
`required_max_latency`, and `evidence_needed_before_live`. The common denominator is a
**point-in-time latency study**: take a candidate live feed, log wall-clock publication time per
event, compare to the official on-field minute, and prove the feature can be computed within the
required latency **without** look-ahead. Until that study exists, every family stays research-only.

## Honest gaps (not papered over)

- **No live-latency measurement anywhere.** This is the single blocker between "research-ready" and
  "live_eligible" for the 6 potential families.
- **xG live feed absent.** Local xG is StatsBomb-open (post-hoc, non-commercial). Live xG/spatial
  data would need a new provider — and prior research says the payoff is unproven.
- **No in-play odds history.** Only pre-match odds exist locally; a live market feature has nothing
  to validate against on disk.
- **Weather as-of history absent.** Venue + schedule are deterministic and local; an
  as-of-timestamped weather source is not in the validated set.
